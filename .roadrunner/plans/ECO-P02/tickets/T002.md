## Objective

Implement the signed Mercado Pago payment webhook, authoritative payment verification, transactional and out-of-order-safe order-state updates, final public-status hardening, and all operational documentation required for one human sandbox checkpoint.

Only a valid signed notification followed by authoritative provider data may change an order's payment state.

## Context

T001 creates the secure order schema, idempotent pending-order flow, Mercado Pago Checkout Pro sandbox preference, public status read, and Supabase Edge Function API.

The public return page is not proof of payment. Query parameters such as `status`, `collection_status`, or `payment_id` must never control the displayed or stored order state.

A separate public Supabase Edge Function must receive Mercado Pago notifications because webhook authentication, CORS behavior, logging, and failure semantics differ from the browser API.

The `MERCADO_PAGO_WEBHOOK_SECRET` will only be generated after the deployed webhook URL is registered in the Mercado Pago sandbox application. Automated tests must use synthetic secrets and current official signature examples or test vectors.

## Expected delivery

Deliver:

- a versioned migration for payment-event persistence and transactional state processing;
- a database RPC that atomically handles idempotency, concurrency, timestamp ordering, and allowed state transitions;
- a public Edge Function named `eco-sp-001-mercado-pago-webhook`;
- current official Mercado Pago signature validation compatible with the Supabase Edge runtime;
- authoritative payment lookup through the Mercado Pago API;
- strict reconciliation against the stored ECO order;
- database-backed or equivalently reliable rate limiting for the public status read;
- safe operational logs;
- comprehensive mocked tests;
- leak scans and final build validation;
- exact human instructions for deploying and validating the complete sandbox flow.

The functional slice must support:

`signed webhook -> authoritative payment -> atomic state transition -> frontend polling shows the stored state`

## Scope

### Payment-event migration and RPC

Add a timestamped migration that creates the minimum event data needed for safe webhook processing.

Create `public.eco_payment_events` or an equivalently explicit structure containing:

- internal UUID primary key;
- provider name;
- provider payment ID;
- stable unique processed-observation or event key;
- external reference;
- authoritative provider status;
- mapped internal order status;
- authoritative provider update timestamp;
- non-sensitive correlation metadata;
- created timestamp.

Enable RLS, revoke access from `anon` and `authenticated`, and create no public policy.

Create a database function such as `process_eco_payment_event` that executes in one transaction and:

- resolves the order using the immutable external reference;
- locks the target order row;
- verifies the stored case, amount, and currency invariants;
- rejects an unknown order or incompatible payment identity;
- recognizes a previously processed observation as an idempotent duplicate;
- stores the provider payment ID safely under its uniqueness constraint;
- compares authoritative provider timestamps;
- ignores older observations that would overwrite newer state;
- prevents `paid` from becoming `pending`, `rejected`, or `cancelled`;
- allows `paid` to become `refunded` only when the authoritative provider state confirms a refund;
- updates the order and inserts the event atomically;
- returns a minimal processing result without buyer data.

The database, not only application code, must enforce the critical transition rules.

### Edge Function: `eco-sp-001-mercado-pago-webhook`

Create:

`supabase/functions/eco-sp-001-mercado-pago-webhook/index.ts`

Register it as a public function with JWT verification disabled in `supabase/config.toml`.

Accept only the supported Mercado Pago payment-notification request shape.

Before implementing cryptography, verify the current official Mercado Pago webhook-signature specification and exact manifest construction. Do not rely solely on the older repository handoff.

Require and validate the current official equivalents of:

- `x-signature`;
- `x-request-id`;
- signed payment resource identifier, including `data.id` where required;
- payment topic or type.

Reject a missing, malformed, or invalid signature with HTTP 401 before any Mercado Pago API call or database access.

Use the official validator only if its package and cryptography are proven compatible with the Supabase Edge runtime. Otherwise implement the currently documented HMAC process with Web Crypto and constant-time comparison, backed by official vectors. Stop and report an incompatibility rather than accepting unsigned notifications.

Accept only payment notifications.

Treat the notification as a resource pointer. Fetch authoritative payment data from Mercado Pago using the server-side sandbox access token.

Validate, at minimum:

- authoritative payment ID matches the signed resource;
- `live_mode` is false or the current equivalent confirms sandbox mode;
- external reference is present and valid;
- currency is `BRL`;
- transaction amount is exactly `79.90`;
- the resolved stored order is case `eco-sp-001` and amount `7990` cents;
- payment identity is compatible with any previously stored payment ID.

Map only these reviewed states:

- `approved` to `paid`;
- `pending` to `pending`;
- `in_process` to `pending`;
- `rejected` to `rejected`;
- `cancelled` to `cancelled`;
- `refunded` to `refunded`.

Treat unknown provider states as unsupported until explicitly reviewed.

Call the transactional database RPC only after signature and provider reconciliation succeed.

Return success only when the event is safely processed or recognized as an idempotent duplicate.

Return a retryable 5xx response for temporary Mercado Pago API or Supabase failures.

Never log request bodies, signatures, tokens, buyer fields, addresses, raw provider responses, or secrets.

Operational logs may contain only:

- event type;
- processing outcome;
- duration;
- non-sensitive request correlation ID;
- truncated or hashed non-secret resource identifiers where necessary.

### Status rate limiting

Add a pragmatic rate limit to the public order-status endpoint.

The implementation must work across Edge Function instances. Do not present an in-memory counter as a reliable distributed limit.

Prefer a small database-backed fixed-window or sliding-window mechanism that:

- stores no raw IP address;
- hashes the client identifier with a server-only salt or uses another privacy-preserving key;
- limits repeated reads per order reference and client window;
- allows the existing browser behavior of one request every five seconds for up to twelve automatic polls;
- returns a controlled 429 without leaking whether unrelated orders exist;
- includes bounded cleanup or expiration behavior.

Keep the mechanism proportional to the low expected traffic. Do not add external infrastructure solely for rate limiting.

## Implementation direction

Keep webhook authentication independent from browser CORS and origin checks.

Signature validation must occur before provider or database operations.

Use authoritative Mercado Pago data as the source of truth and the database RPC as the only state-mutation boundary.

Use provider timestamps and database row locking to handle out-of-order and concurrent delivery.

Use synthetic fixed test vectors. Do not require the real webhook secret for automated tests.

When `MERCADO_PAGO_WEBHOOK_SECRET` is absent in a deployed environment, return a generic controlled service error. Never bypass validation.

Do not acknowledge a notification as successfully processed when the authoritative provider fetch or database transaction failed.

Do not weaken tests merely to accommodate runtime incompatibility. Report the exact incompatibility as a blocker.

## Definition of Done

- A versioned migration creates secure payment-event persistence and the transactional processing RPC.
- Browser roles cannot read or mutate payment events directly.
- The webhook Edge Function is implemented and registered as public without user JWT verification.
- The implementation follows the current official Mercado Pago signature specification.
- Invalid signatures are rejected before provider or database access.
- Authoritative payment data is fetched and reconciled before state mutation.
- Sandbox mode, payment ID, external reference, case, amount, and currency are validated.
- Supported Mercado Pago states map to the documented internal states.
- Duplicate and concurrent delivery produce one database effect.
- Older observations cannot overwrite newer state.
- `paid` cannot downgrade to pending, rejected, or cancelled.
- `paid` can transition to refunded only from authoritative provider data.
- Provider or database failures return retryable errors.
- Public status reads are rate-limited by a distributed, privacy-preserving mechanism.
- Operational logs contain no PII, signatures, tokens, secrets, or raw provider payloads.
- Tests cover signatures, reconciliation, every supported state, idempotency, concurrency, ordering, failures, rate limits, and public status privacy.
- The frontend production build succeeds with synthetic configuration.
- Leak scans pass using synthetic sentinel values.
- Documentation contains a complete human-only sandbox procedure.
- No remote migration, function deployment, frontend deployment, webhook registration, or payment is executed by Codex.
