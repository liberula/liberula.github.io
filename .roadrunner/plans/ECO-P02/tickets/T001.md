## Objective

Implement the server-side API for Case `eco-sp-001` in the dedicated Liberula Supabase project and connect the existing static frontend to a complete Mercado Pago Checkout Pro sandbox flow up to a persisted `pending` order.

The browser must never control the case identity, product title, price, currency, payment status, provider identifiers, return URLs, or canonical case answer.

## Context

The frontend for `/eco/eco-sp-001` and its browser contracts already exist.

The site remains a statically exported Next.js application hosted by Cloudflare Pages. Cloudflare serves only the frontend in this architecture.

A dedicated Supabase project has been created for Liberula. Use Supabase Postgres, migrations, database functions, and Edge Functions for the backend.

A Mercado Pago application for Checkout Pro sandbox has been created. Credentials and the canonical case answer are configured outside the repository or will be verified during the final checkpoint.

Approved server-controlled product values:

- case ID: `eco-sp-001`;
- product title: `Próximo Caso E.C.O. | Lote Fundador`;
- amount: `7990` cents;
- currency: `BRL`;
- quantity: `1`;
- initial order status: `pending`.

The current backend handoffs mention Cloudflare Pages Functions. This plan supersedes that runtime choice. Update the documentation so the repository has one authoritative architecture: Cloudflare Pages for the static frontend and Supabase Edge Functions for the backend.

Do not include the canonical answer or any secret value in code, tests, tickets, documentation, logs, fixtures, commits, or generated assets.

## Expected delivery

Deliver:

- a versioned Supabase migration for secure ECO order persistence;
- database functions needed for atomic order idempotency and preference-creation coordination;
- a public Edge Function named `eco-sp-001-api`;
- server-side answer validation;
- server-side buyer validation;
- idempotent pending-order creation;
- Mercado Pago Checkout Pro sandbox preference creation;
- a minimal public status-read endpoint;
- frontend integration through a public API base URL;
- corrected frontend copy for the real data and checkout behavior;
- automated tests with database and Mercado Pago adapters mocked;
- updated operational documentation for the Supabase architecture.

The functional slice must support:

`correct answer -> buyer form -> one pending order -> sandbox checkout -> pending status read`

## Scope

### Database migration

Create a timestamped migration under `supabase/migrations/`.

Create `public.eco_orders` with, at minimum:

- internal UUID primary key;
- opaque, non-guessable, unique public reference;
- fixed case ID;
- fixed amount in cents;
- fixed currency;
- allowed order status;
- buyer name;
- normalized buyer email;
- normalized buyer WhatsApp;
- separate delivery-address fields;
- unique client idempotency key;
- immutable unique external reference;
- nullable unique Mercado Pago preference ID;
- nullable sandbox checkout URL;
- nullable provider payment ID reserved for T002;
- validated site origin used to construct return URLs;
- created, updated, provider-created, and provider-updated timestamps where applicable;
- fields required to coordinate preference creation safely under concurrent requests.

Add database checks fixing this product to:

- `case_id = 'eco-sp-001'`;
- `amount_cents = 7990`;
- `currency = 'BRL'`;
- the approved status set.

Enable RLS, revoke access from `anon` and `authenticated`, and create no public table policy.

Add indexes and uniqueness constraints for public reference, idempotency key, external reference, preference ID, and payment ID where applicable.

Add an `updated_at` trigger or an equivalent database-enforced update mechanism.

### Atomic order and preference coordination

Create database functions or RPCs that:

- create or return the same order for the same valid idempotency key;
- behave safely under concurrent submissions;
- never create multiple internal orders for one idempotency key;
- atomically claim preference creation for one worker at a time;
- support an expiring claim or another recoverable mechanism when provider creation fails;
- atomically persist the resulting preference ID and sandbox checkout URL;
- allow a same-key retry to recover an existing order whose preference creation previously failed.

A uniqueness constraint alone is not sufficient for the external Mercado Pago call. Use a stable provider idempotency key derived from the internal order and a database-backed claim or an equivalently safe, tested mechanism.

### Edge Function: `eco-sp-001-api`

Create:

`supabase/functions/eco-sp-001-api/index.ts`

Configure it as a public function with JWT verification disabled in `supabase/config.toml`.

Route requests inside the function by method and path.

Implement these logical endpoints beneath the function URL:

- `POST /validate`;
- `POST /orders`;
- `GET /orders/:orderReference/status`.

Share request parsing, JSON responses, CORS, body-size limits, configuration reads, redacted logging, and error handling rather than duplicating them across handlers.

Follow the repository's existing Supabase Edge Function conventions where they remain appropriate, including dependency injection for tests and direct REST or RPC access without exposing administrative credentials.

### Answer validation

For `POST /validate`:

- accept only `POST` and JSON;
- enforce a body limit around 4 KiB;
- require a plain object with exactly the supported `answer` field;
- require a non-empty string within the documented length limit;
- normalize the submitted value and `ECO_SP_001_ANSWER` independently;
- use Unicode NFD;
- remove Unicode diacritic marks;
- use Portuguese-locale lowercase conversion;
- trim leading and trailing whitespace;
- collapse repeated internal whitespace;
- return HTTP 200 with only `{ "correct": true }` or `{ "correct": false }`;
- return generic errors when configuration is missing;
- use `Cache-Control: no-store`;
- never log either answer or the request body.

Do not trust the browser's normalization and do not add a client-side answer fallback.

### Order creation

For `POST /orders`:

- accept only `POST` and JSON;
- enforce a conservative body limit;
- require `Idempotency-Key` as a valid UUID;
- revalidate and normalize every buyer field server-side using the established browser contract;
- reject unknown top-level fields that attempt to supply case, title, price, currency, status, provider IDs, or return URLs;
- derive the site origin only from a validated request origin;
- create or recover the pending order through the database idempotency RPC;
- create a Mercado Pago Checkout Pro sandbox preference server-side only when necessary;
- use one item, quantity `1`, currency `BRL`, and unit price `79.90`;
- use the approved product title;
- populate payer and shipping fields only from validated buyer data where supported;
- use the immutable stored external reference;
- use a stable Mercado Pago idempotency key for the order;
- set `auto_return` to `approved`;
- construct success, pending, and failure return URLs from the validated and stored site origin;
- target `/eco/eco-sp-001/status?order=:orderReference` without provider status as authority;
- set the notification URL to the deployed `eco-sp-001-mercado-pago-webhook` function URL derived from the Supabase project URL;
- persist the preference ID and sandbox checkout URL before replying;
- return only `checkoutUrl` and `orderReference`;
- reject production checkout URLs or live credentials during sandbox implementation;
- use `Cache-Control: no-store`;
- never log buyer data, request bodies, tokens, or raw provider responses.

If another concurrent request owns preference creation, return a controlled retryable response or wait and reload for a short bounded period. Do not issue a second uncontrolled provider request.

### Public status read

For `GET /orders/:orderReference/status`:

- accept only `GET`;
- validate references using `[A-Za-z0-9_-]{16,200}`;
- select only status and `updated_at` through server-side database access;
- return only `status` and `updatedAt`;
- return 404 for an unknown reference;
- return a generic 503 for unavailable configuration or database access;
- use `Cache-Control: no-store`;
- expose no buyer data, internal IDs, addresses, provider IDs, or raw provider data;
- never infer status from return-page query parameters.

T002 will add final rate-limit hardening and provider-driven state transitions.

### CORS and origin handling

Allow only:

- `https://liberula.com`;
- `https://www.liberula.com`;
- localhost origins for development;
- explicit additional origins supplied through a server-side `ECO_ALLOWED_ORIGINS` configuration value.

Do not allow all `pages.dev` origins by wildcard.

Respond correctly to `OPTIONS` for the browser API. The webhook function in T002 must not reuse browser-origin authorization.

### Frontend integration

Add a public build-time variable:

`NEXT_PUBLIC_ECO_API_BASE_URL`

Update the existing frontend contracts so they call:

- `${NEXT_PUBLIC_ECO_API_BASE_URL}/validate`;
- `${NEXT_PUBLIC_ECO_API_BASE_URL}/orders`;
- `${NEXT_PUBLIC_ECO_API_BASE_URL}/orders/:reference/status`.

Keep URL construction and response parsing isolated and tested.

The production build must remain possible when the variable is absent, but the affected flow must fail clearly and safely rather than calling an unintended relative endpoint.

Preserve the existing UI states, idempotency-key reuse, status polling interval, polling limit, and terminal-state behavior unless a concrete incompatibility is found.

## Implementation direction

Keep the API function and provider adapters small enough to test without a running Supabase project.

Prefer the repository's existing fetch-based Supabase integration pattern unless a dependency provides a concrete and tested benefit.

Use the Supabase-provided `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` only inside Edge Functions. Do not require the browser or Cloudflare frontend to possess either value.

Treat all secrets as unavailable to source code and tests. Automated tests must inject synthetic values.

Use only the sandbox Mercado Pago endpoint behavior and reject `live_mode` or production checkout results.

Do not create tables manually through a dashboard. All schema changes must be versioned migrations.

If the current Mercado Pago API does not support the expected idempotency behavior for preference creation, stop and report the exact incompatibility rather than silently weakening concurrency guarantees.
