## Objective

Extend the correct-answer state into a functional provisional commercial flow for the founder batch of Case `ECO-SP-001`.

Collect the buyer information required for the later sandbox checkout integration.

## Context

T001 provides the case route and server-side answer validation.

After a correct answer, the user should see a simple confirmation and a provisional offer.

Approved commercial parameters:

- price: `R$ 79,90`;
- founder batch target: `100` buyers;
- campaign end: `31/08/2026`;
- intended delivery: `15 days`, but the exact start event must not be stated more specifically than the approved product copy already present in the repository;
- buyer fields: name, email, WhatsApp, and address.

The final visual treatment and final legal wording will be handled in another plan.

## Expected delivery

Replace the temporary success state with:

- a concise correct-answer confirmation;
- a provisional founder-batch offer;
- the approved price and campaign facts;
- a buyer data form;
- client-side validation;
- a structured buyer payload ready for T003.

The submit action must not yet create a real order or open Mercado Pago.

## Scope

- Preserve the answer validation flow from T001.
- Add a provisional post-answer offer.
- Display `R$ 79,90`.
- Display the target of `100` buyers.
- Display the campaign end date `31/08/2026`.
- Collect:
  - full name;
  - email;
  - WhatsApp;
  - complete delivery address.
- Structure address fields clearly enough for future fulfillment.
- Add accessible validation and error messages.
- Preserve entered values after correctable validation errors.
- Produce a typed or otherwise well-defined payload for T003.
- Add automated tests for validation where consistent with the repository.
- Keep the layout usable on desktop and mobile.

## Out of scope

- Final marketing copy.
- Final legal refund policy.
- Real order creation.
- Supabase writes.
- Mercado Pago.
- Payment webhook.
- Authentication.
- Magic links.
- Post-purchase content.
- Shipping calculation.
- Production deployment.
- Commit or push.

## Implementation direction

Reuse existing form, component, typography, analytics, and validation conventions when available.

Do not state that refunds are unavailable after production.

Do not invent a more precise delivery-start rule.

Use neutral provisional language where commercial or legal wording is not yet finalized.

The form should prepare a payload containing only data needed by the future order flow.

Do not store buyer data in local storage unless the repository already has an approved pattern for temporary form recovery.

## Definition of Done

- A correct case answer reveals the provisional founder offer.
- The offer displays `R$ 79,90`.
- The offer displays a target of `100` buyers.
- The offer displays `31/08/2026`.
- Name is required.
- Email is required and validated.
- WhatsApp is required and validated conservatively.
- Delivery address is required.
- Validation errors are accessible and field-specific.
- Invalid data cannot proceed.
- Valid data produces the documented buyer payload.
- No order or payment request is created.
- No sensitive buyer data is logged.
- Desktop and mobile layouts remain usable.
- Existing tests pass.
- The production build succeeds.
- No commit, push, or deploy is performed.

## Validation

Run the repository test suite.

Run the production build.

Test the buyer form with:

- all fields valid;
- missing name;
- invalid email;
- missing WhatsApp;
- missing address fields;
- whitespace-only values;
- long but reasonable values;
- accented names and addresses.

Confirm that no network request to Supabase or Mercado Pago occurs.

## Manual test instructions

Open `/eco/eco-sp-001`.

Solve the case.

Review the provisional offer.

Complete the form on desktop and mobile.

Confirm that invalid fields are explained without clearing unrelated valid fields.

Confirm that valid submission reaches a local provisional continuation state and exposes no payment integration.
