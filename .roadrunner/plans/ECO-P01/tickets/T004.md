title: Process Mercado Pago webhooks and confirm sandbox payments
---

## Objective

Confirm Mercado Pago sandbox payment states securely and idempotently, update the corresponding Supabase order, and provide a simple payment-status page.

Only verified provider data may change an order to `paid`.

## Context

T003 creates pending Supabase orders and Mercado Pago Checkout Pro sandbox preferences.

The public return URL is not proof of payment.

Webhook requests must be validated and the payment state must be confirmed through the Mercado Pago API before updating the order.

Expected server-side variables:

- `SUPABASE_URL`
- `SUPABASE_SERVICE_ROLE_KEY`
- `MERCADO_PAGO_ACCESS_TOKEN`
- `MERCADO_PAGO_WEBHOOK_SECRET`

Use sandbox or test configuration only.

## Expected delivery

Add:

- a public webhook endpoint compatible with Cloudflare Pages Functions;
- Mercado Pago signature validation;
- provider API confirmation;
- idempotent event processing;
- internal order-state mapping;
- a simple payment-status route;
- safe polling or refresh behavior for delayed webhook arrival;
- tests for valid, invalid, duplicated, and out-of-order notifications.

## Scope

- Validate the Mercado Pago webhook signature.
- Reject malformed or invalidly signed requests.
- Retrieve authoritative payment information from Mercado Pago.
- Resolve the internal order through the approved external reference.
- Update supported order states, including at least:
  - `pending`;
  - `paid`;
  - `rejected`;
  - `cancelled`;
  - `refunded` when provider data supports it.
- Store provider payment ID and relevant timestamps.
- Process repeated notifications without duplicated effects.
- Handle notifications arriving out of order.
- Add a simple buyer-facing status page.
- Ensure the status page reads server-controlled order state.
- Prevent query parameters alone from marking an order as paid.
- Add structured operational logging without exposing buyer data or secrets.
- Add automated tests with provider and database integrations mocked.
- Document the webhook route and required preview configuration.

## Out of scope

- Production credentials.
- Real payments.
- Final visual design.
- Post-purchase protected content.
- Magic links.
- Transactional email.
- Admin dashboard.
- Fulfillment.
- Automatic refunds.
- Final consumer-policy language.
- Commit, push, deploy, or remote dashboard configuration.

## Implementation direction

Follow the current Mercado Pago webhook-signature specification rather than implementing an inferred format.

If repository code cannot validate the provider signature reliably in the Cloudflare runtime, stop and report the incompatibility instead of bypassing validation.

Treat the webhook as a notification, not the sole source of truth. Confirm payment data through the provider API.

Use database-level uniqueness or transactional safeguards for idempotency when possible.

Do not downgrade a terminal successful state because of an older delayed notification unless the provider's authoritative state explicitly requires it.

The buyer-facing page may use a non-guessable order reference, but it must not expose private buyer fields.

## Definition of Done

- A public webhook route exists.
- Valid sandbox webhook signatures are accepted.
- Invalid signatures are rejected.
- Payment data is confirmed with Mercado Pago before database updates.
- The correct internal order is resolved.
- Approved sandbox payment changes the order to `paid`.
- Pending payment remains `pending`.
- Rejected payment becomes `rejected`.
- Cancelled payment becomes `cancelled`.
- Duplicate webhook delivery has no duplicate effect.
- Out-of-order delivery does not corrupt the final state.
- Query parameters cannot mark an order as paid.
- A simple status page displays the server-controlled state.
- Sensitive values and buyer data are not logged.
- Automated tests cover the required state transitions.
- Existing tests pass.
- The production build succeeds.
- No real payment is attempted.
- No commit, push, or deploy is performed.

## Validation

Run the repository test suite.

Run the production build.

Run automated webhook tests covering:

- valid signature;
- invalid signature;
- malformed payload;
- unknown order;
- approved payment;
- pending payment;
- rejected payment;
- cancelled payment;
- duplicate notification;
- out-of-order notification;
- Mercado Pago API failure;
- Supabase update failure.

With sandbox configuration, complete a test payment and confirm the Supabase state.

## Manual test instructions

Configure the webhook URL and test webhook secret in the Mercado Pago sandbox application.

Complete the full flow:

1. Open `/eco/eco-sp-001`.
2. Submit the correct answer.
3. Complete the buyer form.
4. Open Checkout Pro sandbox.
5. Complete an approved test payment.
6. Return to the site.
7. Confirm that the order becomes `paid`.
8. Repeat or resend the webhook.
9. Confirm there is no duplicated effect.

Also test a cancelled or rejected sandbox payment.

Expected result:

Only authoritative, verified payment information changes the order state.
