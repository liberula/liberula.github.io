# ECO-SP-001 pending order and sandbox checkout handoff

T003 currently includes only the browser contract. No Supabase migration,
Cloudflare Pages Function, remote schema, credential, or Mercado Pago preference
has been created. The later backend plan should implement the steps below.

## Browser contract

The static client sends:

```http
POST /api/eco/eco-sp-001/orders
Content-Type: application/json
Accept: application/json
Idempotency-Key: <random UUID retained for retries>
```

The JSON body contains only:

```json
{
  "buyer": {
    "name": "Buyer name",
    "email": "buyer@example.com",
    "whatsapp": "5511999999999",
    "address": {
      "street": "Street",
      "number": "123",
      "complement": "",
      "neighborhood": "Neighborhood",
      "city": "City",
      "state": "SP",
      "postalCode": "01001000"
    }
  }
}
```

The client does not send case ID, product title, amount, currency, order status,
payment status, return URLs, or provider identifiers.

On success, return HTTP 200 or 201 with only:

```json
{
  "checkoutUrl": "https://sandbox.mercadopago.com/...",
  "orderReference": "opaque-non-guessable-reference"
}
```

The browser rejects non-HTTPS URLs and hosts other than the Mercado Pago sandbox
hosts. All failures remain retryable and retain the same in-memory idempotency
key.

## Future Supabase migration

1. Add a new timestamped SQL file under `supabase/migrations/`.
2. Create `public.eco_orders` with:
   - UUID primary key generated by PostgreSQL;
   - unique, non-guessable public reference;
   - fixed `case_id`;
   - `pending`, `paid`, `rejected`, `cancelled`, and `refunded` status support;
   - integer `amount_cents`;
   - three-character currency;
   - buyer name, normalized email, and normalized WhatsApp;
   - legacy delivery columns nullable for historical compatibility; new digital
     orders collect no delivery address;
   - unique idempotency key;
   - nullable unique Mercado Pago preference ID;
   - external reference linked to the internal order;
   - nullable provider payment ID for T004;
   - created, updated, and provider-status timestamps.
3. Add database checks fixing this product to:
   - `case_id = 'eco-sp-001'`;
   - new orders use `amount_cents = 4990`;
   - `currency = 'BRL'`;
   - an allowed status set.
4. Add uniqueness constraints for the idempotency key, public reference,
   provider preference ID, external reference, and payment ID where applicable.
5. Enable RLS, revoke browser roles, create no public policy, and allow access
   only through server-side service-role operations.
6. Add an `updated_at` trigger or update it explicitly in every server mutation.
7. Apply the migration only to a local or dedicated test project before preview.

## Future Cloudflare Pages Function

1. Create the same-origin function for
   `POST /api/eco/eco-sp-001/orders`.
2. Bind `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, and
   `MERCADO_PAGO_ACCESS_TOKEN` as server-only preview secrets.
3. Reject missing configuration with a generic HTTP 503 response. Never identify
   the missing variable.
4. Enforce POST, JSON content type, a small body limit, same-origin policy, and a
   valid UUID `Idempotency-Key`.
5. Revalidate every buyer field using the T002 contract. Never log the body or
   buyer values.
6. Define these values as server constants:
   - case ID: `eco-sp-001`;
   - amount: `4990` cents / `49.90`;
   - currency: `BRL`;
   - product title approved by the later backend plan;
   - initial status: `pending`.
7. Insert or recover the pending order through the unique idempotency key.
   Concurrent requests with the same key must resolve to the same order.
8. If that order already has a valid preference, return its existing sandbox
   checkout URL/reference rather than creating another order or preference.
9. Create the Mercado Pago preference server-side with
   `POST https://api.mercadopago.com/checkout/preferences`, a Bearer sandbox
   access token, and an API idempotency key where supported.
10. Set one digital item with quantity `1`, currency `BRL`, and numeric unit
    price `49.90`. Populate only payer contact fields; do not create shipping
    data for the digital mission.
11. Set `external_reference` to the internal order identifier or another unique
    immutable value stored on that order.
12. Configure HTTPS `back_urls` on `liberula.com` for `success`, `pending`, and
    `failure`, all targeting
    `/eco/eco-sp-001/status?order=:orderReference` with only the opaque public
    reference. Mercado Pago exposes these three return categories; use the
    failure return for checkout cancellation as well. Do not add provider status
    parameters as application authority.
13. Configure the future T004 `notification_url` and use `auto_return:
    "approved"`.
14. Persist the returned preference ID and sandbox checkout URL before returning
    to the browser. If provider creation fails, retain a recoverable pending
    order and allow a same-key retry.
15. Return only `checkoutUrl` and `orderReference`, with
    `Cache-Control: no-store`.

- absent configuration;
- server-fixed case, amount, currency, title, and initial status;
- successful pending-order insert and preference creation;
- external-reference linkage and all return URLs;
- provider or database failure;
- duplicate and concurrent idempotency-key submissions;
- retry after an order exists but preference creation failed;
- rejection of production credentials or production checkout URLs in sandbox;
- generic non-leaking logs and errors.

create one order, inspect its fixed fields, open the returned
`sandbox_init_point`, cancel, and retry with the same idempotency key. Do not use
production credentials or complete a real payment.
